# Plurora 章程

> [English](./CHARTER.en.md) · [中文](./CHARTER.md)

Plurora 是一个面向人、AI 与软件共同创造和运行的开放数字平台。

它让应用、工具、服务、世界、游戏、agent、创作环境，以及今天尚未被命名的数字形态，能够被创建、组合、运行、审视、修改、迁移和替换。平台提供可靠的共同基础，但不规定这些形态最终应该长成什么样。

这份章程定义 Plurora 长期不轻易改变的身份、目标与边界。

## 平台身份

Plurora 不只是一个内核，也不等于某一套官方界面。完整的平台包括：

- 一个尽量小、只拥有通用机制的宪法基底；
- 可演化、可竞争的公开协议与组件生态；
- 负责现实机器、网络和数据生命周期的 Host / runtime 基础设施；
- 一套真正完整、好用，但可以被替换的官方发行版；
- 建立在其上的第三方产品、工具、服务与体验。

下层为上层提供能力，上层不能反过来把自己的产品本体写成整个平台的物理法则。

## 长期建设目标

### 1. 尽可能开放

开放不只意味着源代码可见。Plurora 还要做到：

- 第一方实现、协议、数据格式和扩展入口公开；
- 用户能读取、导出、备份、迁移和删除自己的数据；
- 官方实现不拥有私有 API、隐藏权限或不可替代的路由优先级；
- 客户端、模型、agent、组件、存储、执行器、Host 与上层产品都可以被替换；
- 本地、自托管和离线使用不是二等路径；
- 第三方能够在不依赖仓库内部知识的情况下平等参与。

### 2. 尽可能扩大可能性与多样性

平台不定义唯一的应用形态、工作流、交互方式或内容本体。不同产品可以选择不同的协议、Shell、组件、数据模型和运行方式；彼此完全不同的系统可以共存在同一个平台生态中。

多样性来自独立可替换的维度，而不是给一个固定产品增加越来越多的开关。

### 3. 尽可能采用先进而有价值的技术

Plurora 主动采用能显著增加自由度、安全性、性能、可移植性和可维护性的技术，例如 capability security、内容寻址、可移植组件、local-first、多 Host、流式与可取消执行、明确因果、效果收据和协议协商。

“先进”不等于追逐新名词。只增加复杂度、却没有带来实际能力或长期收益的技术，不进入平台核心。

### 4. 尽可能长久地演化

平台必须允许自身持续变化，而不把用户数据和生态一起撕碎：

- 稳定层尽量小，上层可以竞争、分叉和替换；
- 公开合同有成熟度、版本、兼容窗口、弃用和迁移机制；
- 未知字段和未知工件可以被保留、复制和转移；
- 旧内容不依赖某个仍然在线的官方服务才能被读取；
- 错误抽象可以退出，而不是永久堆积；
- 实现框架、语言和供应商不成为平台宪法。

### 5. 尽可能好用

开放平台不能以中立为理由把复杂度全部交给用户。官方发行版必须提供连贯、可靠、可恢复的默认体验：安装后能使用，简单任务保持简单，复杂能力按需展开，权限与风险可以理解，错误有恢复路径，数据管理清楚，创作者能快速开始。

官方体验可以有强观点，但它只能通过公开边界实现；好用不能靠平台特权换取。

## 不可妥协的原则

### 用户拥有自己的数据与选择

平台保存的是用户的工作、历史和配置，不是平台的锁定筹码。可移植性、备份、恢复和删除是基本能力，不是发布后的附加功能。

### 权力必须显式

任何跨边界行为都必须能回答：谁、对什么资源、在什么条件下、获得了什么权力、权力从哪里来、何时失效。声明上限不等于实际授权；凭据不能替代资源作用域和策略。

### 官方实现没有特权

官方包、Shell、Host profile、客户端和服务使用与第三方相同的注册、授权、调用、审计和迁移机制。维护者身份可以表达责任，不能表达隐式权威。

### 公开合同高于内部便利

同进程调用、HTTP、stdio、WASM、远程服务和客户端界面可以有不同传输，但必须保留相同的身份、权限和行为语义。内部实现不能依赖生态参与者无法使用的旁路。

### 基底只拥有无法安全上移的机制

对话、模型、agent、记忆、世界、游戏、文档、项目工作流、编辑器和部署产品语义都不是宪法基底。共同语义属于协议，机器操作属于 Host，交互观点属于发行版或产品。

### 组合与替换优于中心化

组件、协议、客户端和产品能够独立替换。一个官方默认值不能静默成为永久唯一值；歧义通过显式选择、Profile 或策略处理，而不是通过官方优先级解决。

### 默认产品不是平台法律

官方发行版是 Plurora 的重要组成部分，也应当是一款真正优秀的产品；但它使用的 Home、Project、Play、Forge、Assist 或任何未来工作流，只约束选择它的发行版和 Profile，不能反向约束所有 Plurora 产品。

### 演进必须保留迁移路径

稳定不等于永远只加字段。破坏性变化必须有版本边界、迁移工具、兼容期和可读取旧数据的路径。

### 质量保障服务于建设目标

测试、conformance、fixture、dogfood 和参考实现用于发现问题、防止退化和提高可信度。它们不决定平台为什么存在，也不应成为为了“证明某个抽象”而制造功能的理由。

## AI 在平台中的位置

AI 是第一等参与者，但不是平台唯一中心。Human、assistant、agent、普通软件组件和自动化服务都通过明确身份与能力工作。模型、prompt、memory、agent loop 和推理策略由可替换协议与组件拥有，不进入宪法基底。

## 非目标

Plurora 不追求：

- 把所有数字产品统一成一种本体或一个工作流；
- 用功能数量、测试数量或新技术数量衡量方向是否正确；
- 让官方发行版成为第三方必须复制的唯一形态；
- 以开放为借口长期容忍难用、不完整或不可恢复的体验；
- 以好用为借口建立私有协议、隐藏权限或数据锁定；
- 把任意远程 shell、无限权威或未声明副作用包装成“灵活性”。

## 稳定性承诺

这份章程只通过显式修订改变。未来功能若与章程冲突，首先重新设计功能和所属层，而不是把产品便利偷偷提升为平台原则。
