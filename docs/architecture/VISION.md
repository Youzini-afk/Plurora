# 愿景

> [English](./VISION.en.md) · [中文](./VISION.md)

Yggdrasil 最终要成为一块可以长期依赖的开放数字土壤：普通用户能直接使用，创作者能快速构建，专业开发者能深入扩展，运营者能可靠运行，而平台作者没有预见过的新形态仍然有生长空间。

AI 原生能力是重要方向，但平台不以聊天、agent、世界、游戏或任何单一产品形态定义自己。

## 希望达到的整体形态

```text
┌──────────────────────────────────────────────────────────┐
│ Products / Experiences / Services                        │
│ 应用、工具、世界、游戏、agent workspace、服务、未知形态       │
├──────────────────────────────────────────────────────────┤
│ Distributions / Shells / Clients                         │
│ 官方发行版、第三方发行版、Web、Desktop、CLI、移动端、IDE       │
├──────────────────────────────────────────────────────────┤
│ Protocol Commons / Components / Content                  │
│ 可竞争协议、可替换组件、内容、composition、adapter             │
├──────────────────────────────────────────────────────────┤
│ Constitutional Substrate                                 │
│ 身份、权力、对象、日志、因果、调用、流、事务、效果、协商          │
└──────────────────────────────────────────────────────────┘

Host Control Plane / Runtime Fabric 横跨这些层：
安装、进程、WASM、远程执行、文件、secret、网络、端口、部署、备份、诊断。
```

这张图不是一条只能自上而下的产品栈。不同发行版和产品可以选择不同协议、组件和 Host 能力；唯一不能绕过的是明确的身份、权力和公开边界。

## 开放在实际使用中的样子

一个用户应当能够：

- 在本机使用 Yggdrasil，而不被迫注册某个云账户；
- 把数据、历史、配置、composition 和内容完整带走；
- 更换模型、组件、客户端、存储和 Host，而不是重建全部工作；
- 查看哪些代码、服务和身份拥有何种权力；
- 拒绝官方默认值，选择第三方实现或自己的实现；
- 在官方服务消失后仍然读取重要数据。

一个第三方作者应当能够只凭公开文档、SDK 和协议完成接入，不需要复制官方仓库内部代码，也不需要获得白名单身份。

## 多样性如何产生

平台把以下维度尽量解耦：

```text
内容与数据模型
× 协议语义
× 组件实现
× 交互与 Surface
× 模型与 Agent
× 执行与隔离方式
× 存储与检索
× 本地 / 远程 / 多 Host
× 单人 / 协作 / 自动化
```

产品可以只选择其中一小部分。一个纯本地工具不必携带部署系统；一个无头服务不必拥有 Home；一个世界产品不必使用 Project Console；一个普通 Web 应用不必采用 agent 或模型。

这要求 Yggdrasil 区分机制、协议、发行版和产品，而不是把所有概念都塞进“内核或能力包”二选一。

## 技术方向

Yggdrasil 的技术野心集中在能长期提高能力的基础上：

- **Capability-oriented security：** 最小权威、衰减、委托、租约、撤销和可理解的授权链；
- **Content-addressed data：** 重要对象有可验证身份，引用不依赖本机路径；
- **Portable components：** WASM、隔离进程、远程边界和可信 native 可以实现相同协议，但明确披露不同信任保证；
- **Local-first and multi-Host：** 本机优先、离线可用，同时能安全扩展到远程设备和多节点；
- **Streaming execution：** 流、取消、deadline、背压、恢复和长任务观测是基础能力；
- **Causality and effects：** 历史回放与重新执行分离，非确定性和外部效果留下可审计收据；
- **Protocol evolution：** 显式协商、成熟度、兼容 Profile、弃用、迁移和 legacy adapter；
- **Implementation independence：** 数据和协议不绑定某一语言、UI 框架、模型供应商或云平台。

这些方向不要求一次性全部进入稳定层。成熟度和实际收益决定它们停留在 Experimental、Candidate 还是 Stable。

## 长期演化方式

Yggdrasil 不把“兼容”理解为永远保留所有错误决定。长期演化依靠：

- 极小的稳定基底；
- 可版本化和可竞争的协议公地；
- 独立寻址的组件、内容与协议描述；
- 兼容读取、显式迁移和可撤销的 adoption；
- 对未知工件的保真保存；
- 清楚区分历史事实、当前状态和重新执行结果；
- 允许官方发行版被重写，而用户数据和第三方组件仍然存在。

当前 Contract V1 是可运行的公开合同，不自动等同于永久宪法。长期归属与迁移边界见 [`CONSTITUTION_V2.md`](CONSTITUTION_V2.md) 和 [`../spec/CONTRACT_LAYERING_MATRIX.md`](../spec/CONTRACT_LAYERING_MATRIX.md)。

## 好用的默认发行版

Yggdrasil 的官方发行版不是只供演示的参考壳，而应当是普通人愿意长期使用的产品。它需要：

- 安装后即可在本机工作；
- 清楚地发现、安装、运行、停止、更新和删除内容；
- 用人能理解的方式展示权限、风险、状态和恢复选项；
- 给创作者提供模板、调试、热更新、组合、资源管理和 AI 辅助；
- 让本地与远程连接、备份、迁移和故障恢复尽量直接；
- 对简单用户隐藏不必要的复杂度，对专业用户保留深入能力；
- 通过公开协议实现全部功能，从而允许第三方发行版走不同路线。

官方发行版可以采用 Project、Home、Workbench 或其他组织方式，但这些是产品选择，不是所有上层系统的本体要求。

## 平台与产品的关系

平台负责扩大可选择空间并提供可信共同基础。产品负责作出观点明确的选择，把其中一条路径做完整、做顺畅。

因此：

- 平台不能因为追求中立而拒绝建设优秀默认体验；
- 产品不能因为追求便利而要求平台永久接受自己的本体；
- Host 可以拥有现实机器操作语义，但不能把某个产品的内容语义放进基底；
- 协议可以约束选择它的参与者，但不能声称自己是唯一可能的协议；
- 一个成功的官方产品应当使平台更好用，同时保持自己可被替换。

## 希望看到的结果

Yggdrasil 逐渐成熟时，应该同时出现：

- 非技术用户能够安装并稳定使用的官方发行版；
- 第三方可以发布的组件、协议、Shell 和完整产品；
- 本地、远程、无头和嵌入式等多种部署形态；
- AI 密集型产品与完全不依赖 AI 的产品；
- 能跨实现、跨机器和跨时间保存的数据与历史；
- 平台作者未预见、也未特别授权的新用途。

这不是由某个单一功能、示例或验收题定义的终点，而是持续建设时需要共同保持的方向。
